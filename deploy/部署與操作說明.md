# Linux 部署與 YOLO 回饋訓練流程

此版本把網站前端、Python YOLO 辨識／標註／訓練服務部署到 Linux。既有 Supabase 專案仍負責登入、資料庫、照片儲存及 `ai-stockin-confirm` 入庫確認；不是把 Supabase 整套搬到 Linux。新版程式位於目前這份巢狀的 `ResourceSharingPlatform-Web-main` 資料夾，請連同 `src`、`supabase`、`ai-recognition-lab`、`modules/vision`、`deploy`、package lock 一起移轉。

## 1. 部署到目標電腦

Linux 先安裝 Docker Engine 與 Compose v2。以下指令從專案根目錄執行：

```sh
cp deploy/.env.example deploy/.env
# 用文字編輯器填入 deploy/.env，勿提交或分享金鑰。
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
```

第一次建置需下載 Node/Python 套件、CPU PyTorch 及 YOLO11n 權重。網站預設在 `http://目標電腦IP:8080/`，仍使用原專案的 `/#/` 路由。`APP_ORIGIN` 必須與實際瀏覽器網址的「協定、主機、連接埠」完全相同，不含 `/#/` 或其他路徑；從另一台電腦連線時不可維持 localhost。公開網站請在 Nginx 前配置 HTTPS，並將 APP_ORIGIN 改成實際 HTTPS 網址。Supabase 的 Site URL / Redirect URLs 也要允許新網站位址。

必要設定：

| 設定 | 用途 |
|---|---|
| SUPABASE_URL | 原系統 Supabase 專案網址 |
| SUPABASE_ANON_KEY | 原前端公開金鑰，前端建置也會使用 |
| SUPABASE_SERVICE_ROLE_KEY | 後端讀目錄、讀照片、寫辨識紀錄；不可放入 VITE 變數 |
| APP_ORIGIN | 實際網站來源，阻擋非預期來源的寫入請求 |
| OPENAI_API_KEY | 後端 OpenAI 複核使用；可暫留空測試 YOLO 與人工確認 |
| OPENAI_MODEL | 「簡易物件」複核模型，預設 gpt-4.1-mini |
| OPENAI_COMPLEX_MODEL | 「複雜物件」複核模型，預設 gpt-4.1 |
| YOLO_REVIEW_THRESHOLD | 預設 0.65；任一 YOLO 框低於此信心值觸發複核 |

模型名稱可改成帳號可用、支援圖片且相容 Chat Completions 的 OpenAI 模型。兩個選項使用同一個 OPENAI_API_KEY。這些是此部署版本的設定，不會讀原本「AI 智慧入庫設定」頁中的金鑰；該頁仍供舊的文字辨識 Edge Function 使用。改 `.env` 後再次 `up -d --build` 套用。

原專案 Supabase migrations、`ai-stockin` 儲存桶及 Edge Functions 必須已部署。使用原有 Supabase 專案時沿用現有設定；新建 Supabase 專案則依專案原有部署文件初始化。本次沒有新增資料表，回饋與模型存在 Linux 的持久化 volume。

## 2. 網頁辨識流程

```text
登入 → AI 智慧入庫 → 上傳照片至自己的 Supabase 路徑
  → Python 驗證登入、角色、據點與照片所有者
  → 目前啟用的 YOLO 偵測每個可見物件
  → 目錄／同義詞對照 → 依框數計算品項與數量
  → 沒找到物件／低信心／目錄外品項／手動要求複核
      → OpenAI 看整張照片重新辨識 → 取代初步結果，避免相加重複計數
  → 寫入待確認辨識紀錄 → 使用者核對 → 原有入庫確認
```

只按可見外包裝計數，一箱算一箱，不猜箱內數量。YOLO 的信心值不是辨識準確率；高信心也可能漏判，因此所有結果仍需人工確認，亦提供「本次一定交由 OpenAI 複核」。通用模型原本的類別有限，初期目錄品項不匹配時較容易呼叫雲端；中文名稱可透過既有同義詞目錄映射，例如 bottle 對應瓶裝水，但前提是業務定義確實相符。

若 OpenAI 未設定、429、逾時或格式錯誤，保留初步框供修正，數量留待人工填寫，不會自動重試產生額外請求。OpenAI 複核後仍低信心或不在目錄，也需人工填數量。輸出品項必須選回標準目錄，未知品項由管理員先新增。手機影像入庫入口在啟用此服務時也導向同一辨識頁。純文字辨識維持原 Edge Function。

## 3. 錯誤回饋與管理員審核

1. 辨識結果下展開「辨識錯誤？框選並提交正確答案」。
2. 每個物件一個框，改錯誤品名、刪錯框、補漏框；沒有目標物件時勾空場景。
3. 勾選已核對後提交。這只保存訓練回饋，不會改動庫存或入庫表單；表單仍需另行核對。
4. 管理員開啟「YOLO 回饋與訓練」，載入待審回饋，核對並保存。
5. 選 train / val / test 及拍攝群組，再按「將目前已核對回饋納入資料集」。

一般幹部只能提交自己的據點及自己的辨識回饋；訓練、匯出、審核和發布限管理員。原圖、初步 YOLO 框、複核來源、修正版本保留供追蹤。原始回饋不會未經審核就拿來訓練，也不會把模型猜測直接當正確答案。

## 4. 訓練、評估、發布與回復

- 先建立品項，再收集逐物件框選標註。相同照片不可跨集合，相同場景連拍填相同拍攝群組並放同一集合。
- train 讓模型學習，val 選擇權重，test 保留最後驗證。至少需要有框的 train、val 圖片，發布前另需 test；少量圖片僅供流程測試。
- 選起始模型及輪數，按「開始訓練」。每次建立固定資料快照；後續修改不影響已啟動的工作。
- 訓練完成後，到「比較結果」選新模型，按「評估此模型的保留測試集」。歷史會顯示 `exactItemAndCountRate`（每張品項與數量完全正確的比例）、`meanAbsoluteCountErrorPerImage`（每張各品項數量絕對誤差總和的平均）以及框的精確率／召回率；完整報告（各品項表現、門檻掃描、校準）可由 `GET /api/v1/evaluation/<工作ID>` 取得。
- **發布門檻：** 新模型必須和目前上線模型在同一份保留測試集上比較，且完全正確率不下降、數量誤差不增加，才能啟用。第一次啟用專屬模型前，請先選「YOLO11n 通用預訓練」也評估一次。保留集照片有增減或修改後，兩個模型都要重新評估。容許幅度在 `modules/vision/config/vision.yaml` 的 `release` 區段。
- **複核門檻校準：** 啟用時會套用該模型評估所得的各品項門檻（門檻以上精確率達 90% 的最低信心值）；保留集框數不足 5 個的品項沿用 `YOLO_REVIEW_THRESHOLD`。「改善建議」頁會顯示目前各品項的門檻。
- 評估與門檻都只是輔助，管理員仍需依實際結果決定是否發布；系統不會自動發布。
- 要回復舊版，從同一選單選先前發布過的模型再按啟用（回復不受退步檢查限制）；也能切回 pretrained 通用模型。
- 「改善建議」頁彙整各品項的資料量、YOLO 漏判、上線模型表現，列出下一步該補拍的品項。

此 Compose 預設 CPU。GPU 訓練需要依目標機器 NVIDIA 驅動、Container Toolkit、PyTorch CUDA 版本另行配置；單純在工作台選 GPU 0 不會替容器安裝 CUDA。服務使用單一 Gunicorn worker，避免多進程同時寫檔或管理同一訓練工作。訓練會佔用 CPU，建議在非尖峰時段操作；重啟中斷的訓練不會自動續跑。

後續加入失敗照片時，保留原有正確案例一起訓練。不要反覆用 test 調參；持續調整後應新增獨立測試照片確認泛化。

## 5. 保存與備份

`vision-data` volume 保存原圖、回饋、classes.json、標註、快照、訓練權重及 deployment.json。重建容器不會清掉它；**不要使用 `docker compose down -v` 刪除訓練資料**。定期備份整個 volume，單純匯出 ZIP 只包含資料集，不包含回饋歷史和模型。搬移本機 yolo-data 到 Linux 後，先重新評估模型再發布：舊版評估沒有保留集指紋，也可能記錄 Windows 模型路徑。

映像只從 `modules/vision` 建置（`deploy/Dockerfile.vision`），資料目錄仍是 `/data`，因此既有 `vision-data` volume 可直接沿用；預訓練權重改放在映像內 `/app/models`。

可用以下方式從執行中的容器備份（請先等訓練和回饋寫入完成）：

```sh
mkdir -p backups
docker compose --env-file deploy/.env -f deploy/compose.yaml cp vision:/data ./backups/vision-data
```

## 6. 已驗證與部署後驗收

驗證細節見 `modules/vision/驗證紀錄.md`。尚未在 Docker 中建置映像，也沒有用真實金鑰呼叫正式 Supabase／OpenAI。移轉後需完成：登入 Admin/Cadre、上傳照片、YOLO 複核、確認入庫、修正回饋、審核、訓練、評估、發布及重啟後模型設定保留的完整驗收。建議先在第 7 節的本機 Supabase 環境走完一次。

本機測試指令（Linux 使用自己的 Python 虛擬環境）：

```sh
npm run build
npm run lint
cd ai-recognition-lab && npm test && cd ..
cd modules/vision && python -m unittest discover -s tests -v
```

## 7. 本機 Supabase 整合測試（Windows）

不動正式 Supabase，在本機跑完整流程（登入 → AI 智慧入庫 → YOLO 辨識 → 回饋 → 審核 → 訓練 → 發布）。

需求：Docker Desktop（WSL 2）執行中、Node.js、`ai-recognition-lab\.venv-yolo`（執行 `安裝YOLO.cmd` 建立）。

1. 雙擊 `deploy\local\啟動本機整合測試.cmd`。腳本會：
   - `supabase start`：啟動本機 Supabase，套用 `supabase/migrations`，建立 `items`、`ai-stockin` 儲存桶，載入 `supabase/seed.sql` 的測試帳號（第一次需下載映像）。
   - 產生 `.env.development.local`（前端，只在 npm run dev 使用，不影響正式建置）與 `deploy\local\.env.vision`（辨識服務）。兩者都已排除在版本控制外。
   - 另開視窗啟動辨識服務（127.0.0.1:8000，主系統整合模式）與前端（http://localhost:5173，`/vision-api` 由 Vite 代理到 8000）。
2. 開啟 http://localhost:5173 ，用 `supabase/seed.sql` 開頭列出的 `local_admin` 或 `local_cadre` 登入。
3. **OpenAI 複核會計費：** 只要 Windows 環境變數有 `OPENAI_API_KEY`，腳本就會帶給辨識服務，需要複核的照片會實際呼叫 OpenAI（啟動時會以黃字提示）。不想呼叫時，先在同一個 PowerShell 執行 `$env:OPENAI_API_KEY=$null` 再用 `start-local.ps1` 啟動；此時需要複核的照片改為人工核對。
4. 需要清空本機資料庫並重新套用 migration：`powershell -ExecutionPolicy Bypass -File deploy\local\start-local.ps1 -Reset`。
5. 停止：關閉辨識服務與前端視窗，再執行 `deploy\local\stop-local.ps1`。

預設辨識資料目錄為 `ai-recognition-lab\yolo-data-local`，第一次啟動時從 `yolo-data` 複製一份。整合模式每次辨識都會把主系統目錄品項加入標註類別、保存回饋照片，用複本可避免動到 `yolo-data` 的正式標註。要直接使用某個資料夾，加參數 `-VisionDataDir <路徑>`；同一個資料夾不能同時被舊測試入口（5180/5181）和本機整合服務使用。

Studio（資料庫管理介面）：http://127.0.0.1:54323 。之後新增資料表時，migration 會先在這個環境以 `-Reset` 驗證，再部署到正式專案。
