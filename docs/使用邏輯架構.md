# 使用邏輯架構

描述系統「怎麼運作」的規則層：角色權限、資料範圍、狀態流轉、關鍵業務邏輯。

## 一、角色與權限

> 角色 `role_name` 值仍為 `Admin`/`Cadre`/`SocialWorker`（RLS/約束依此），**僅顯示名稱**改名。

| 角色（顯示名） | 值 | 資料範圍 |
|---|---|---|
| **總管理人員** | `Admin` | 全部據點、全部功能 |
| **據點管理人員** | `Cadre` | 所屬據點；可轉移、報廢 |
| **物資小天使** | `SocialWorker` | 所屬據點；查詢、入庫、領用、影像入庫 |

功能可用性（前端 `RoleGate` + 後端 Edge Function 雙重把關）：

| 功能 | 總管 | 據點管理 | 物資小天使 |
|---|:--:|:--:|:--:|
| 戰情總覽 / 狀態清單（舉手） / 物資清單 / 各紀錄查詢 | ✅ | ✅ | ✅ |
| 物資入庫 / 出庫 / AI·手機影像入庫 | ✅ | ✅ | ✅ |
| 捐贈紀錄補登/編輯/刪除 | ✅ | ✅ | ✅（限所屬據點） |
| 物資轉移 / 物資報廢 | ✅ | ✅ | ❌ |
| 物資明細（異動歷程＋盤點調整） | ✅ | ❌ | ❌ |
| 系統管理（帳號/據點/庫存種類/LINE/AI 設定） | ✅ | ❌ | ❌ |

> 非總管只能對「所屬據點」操作；沒有據點的帳號無法執行異動。

## 二、資料範圍（RLS）落實方式

- `supply_item` 等：`select` 限 `is_admin() OR location_id = my_location_id()`。
- 扣庫存寫入不開放 client 端；由 Edge Function 內先驗證 `role_name`、`location_id`，再以 `service_role` 寫入。
- 手機頁面一律以 `profile.location_id` 過濾（不分角色）；管理員若未指定據點則看全部。

## 三、物資的兩層資料模型

```
目錄（可選用的品項）                實際庫存（真的有的東西）
inventory_item_definition  ──┐
  (種類/名稱/單位/全域安全庫存) │
inventory_item_variant       │      supply_item（一個「批次」）
  (規格)                      └────→ 同一種類/名稱/規格 + 同效期 視為一批
location_inventory_safety_stock       有自己的數量、效期、據點、圖片
  (各據點門檻)
```

- 「入庫」是選目錄品項建立/加總 `supply_item` 批次。
- 「出庫/捐贈/報廢/轉移」是對既有 `supply_item` 批次加減量。
- **數量只能透過異動改變**（出/入/捐/廢/轉），物資清單的「編輯」用於修正效期/安全庫存/備註/圖片。

## 四、庫存狀態判定

| 狀態 | 條件 |
|---|---|
| 據點低庫存 | 該據點該品項**現有總量 1～據點門檻**（有貨才算，完全沒貨不列入）；判斷統一走 `lib/lowStock`（查 `location_low_stock_view`），戰情總覽/物資清單/狀態清單一致 |
| 總量不足（啟動募資） | 該規格**全據點加總 < 門檻 − 安全庫存量**（`global_low_stock_view`） |
| 已過期 | `expiration_date < 今天` |
| 即將過期 | 今天 ≤ `expiration_date` ≤ 今天+30 天 |
| 正常 | 以上皆非 |

- 據點門檻在 `location_inventory_safety_stock`（依種類+名稱）；全系統募資門檻在 `inventory_item_variant`（依規格，`global_threshold`/`global_safety_stock`）。
- 戰情總覽的「據點低庫存」數字與各據點狀態，皆對**實際物資批次**計數（非門檻筆數），與點進去的清單一致。

## 五、轉移狀態機

`Pending`（建立即扣來源）→ `Confirmed`（目的地加量、合併同批次）或 `Cancelled`（退回來源，並還原被軟刪的來源列）。合併批次的判準：**種類 + 名稱 + 規格 + 效期**一致即同批（variant 連結僅在兩邊都有值且不同時才排除）。

## 六、AI 影像入庫原則

- 一律先進 `ai_stock_in_log`（待確認），**人工確認後**才寫正式庫存。
- 目錄比對：精確 → 同義詞（`catalog_synonym`）→ 目錄名稱 → 都沒有就當新品項。
- 確認後照片從 `ai-stockin` 搬進 `items` 集中管理。

## 七、LINE 通知邏輯

- **被動式**：只在異動成功後觸發，不背景輪詢。
- **去重複**：對目前警示清單算簽章，與上次相同就不重發。
- **對象**：只推給「已用綁定碼綁定且開啟通知」的帳號。

## 八、缺料舉手 → 轉移補貨

- 狀態清單（低庫存/即期/總量不足）可「舉手」提出需求：**需求方＝登入者所屬據點**、**來源＝物資所在據點**（總量不足時挑有貨的據點）。
- 寫入 `supply_request`（Open）→ 戰情總覽「待處理需求」→「轉移補貨」帶 `?requestId=` 到轉移頁自動帶好來源/目標/品項 → 完成或取消可標記需求狀態。
- 「已過期」清單不舉手，改為直接「報廢」（帶批次進報廢頁，限總管/據點管理人員）。

## 九、盤點調整（物資明細）

- 「調整」＝把某批次目前數量修正為盤點值，並在明細留一筆「調整」異動（`stock_adjust`，總管專用）。
- 「刪除」只對「調整」這種列開放，會把當初增減回算回去（`stock_adjust_delete`）；出庫/報廢/轉移不在此刪，走各自回庫/取消。

## 十、共通 UX 規則

- **送出前確認**：入庫/出庫/報廢/轉移送出前先跳「確認視窗」核對品項與數量（`ConfirmActionModal`），按確定才真正寫入。
- 建立/確認成功後 → 導回對應的清單/紀錄頁，並顯示成功訊息（`FlashMessage`）。
- 列表都有「篩選條件」卡（關鍵字＋維度下拉＋重設）；紀錄/分析頁多可「匯出 Excel（篩選後）」。
- Edge Function 失敗時還原真正的中文錯誤訊息（`functionError`）。
