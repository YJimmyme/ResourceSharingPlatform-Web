# 系統架構

## 一、整體架構

本系統是「靜態前端 + BaaS 後端」的架構：前端是純靜態檔案（HTML/CSS/JS）託管在 GitHub Pages，沒有自己的應用伺服器；所有伺服器端能力（資料庫、驗證、檔案、交易邏輯）都由 Supabase 提供。

```mermaid
flowchart TB
    subgraph Client["使用者端"]
        Browser["瀏覽器 / LINE 內建瀏覽器<br/>React SPA (HashRouter)"]
    end
    subgraph GH["GitHub"]
        Pages["GitHub Pages<br/>靜態檔案託管"]
        Actions["GitHub Actions<br/>build & deploy"]
    end
    subgraph Supabase["Supabase 專案"]
        Auth["Auth<br/>(帳密→假 email)"]
        DB[("Postgres<br/>+ RLS + Views + RPC")]
        Storage["Storage<br/>items / ai-stockin"]
        Edge["Edge Functions (Deno)<br/>交易邏輯 / AI / LINE"]
    end
    subgraph External["外部服務"]
        OpenAI["OpenAI / Anthropic Vision"]
        LINE["LINE Messaging API"]
    end

    Browser -->|載入靜態檔| Pages
    Browser -->|supabase-js| Auth
    Browser -->|supabase-js (RLS)| DB
    Browser -->|上傳/讀取圖片| Storage
    Browser -->|functions.invoke| Edge
    Edge -->|service_role| DB
    Edge --> Storage
    Edge --> OpenAI
    Edge --> LINE
    LINE -->|webhook| Edge
    Actions -->|deploy| Pages
```

## 二、為什麼這樣拆

| 決策 | 原因 |
|---|---|
| **HashRouter 而非 BrowserRouter** | GitHub Pages 無伺服器端 rewrite；`#/path` 讓深連結重新整理不會 404 |
| **商業邏輯放 Edge Function** | 扣庫存、跨據點轉移等牽涉多筆/交易的操作，需要伺服器端驗證＋Postgres 交易，不能只信任前端 |
| **單表 CRUD 走 supabase-js + RLS** | 據點/物資/設定等單表操作，用資料列級安全（RLS）即可控管，不需 Edge Function |
| **帳密登入轉假 email** | 保留原系統的帳號登入體感；後台把 `{帳號}@local.invalid` 餵給 Supabase Auth |
| **圖片實體檔名用 ASCII** | Supabase Storage 物件鍵不收非 ASCII；中文命名改用「下載檔名」(Content-Disposition) 呈現 |

## 三、技術選型

| 層 | 技術 |
|---|---|
| 前端框架 | React 19 + TypeScript + Vite 8 |
| 路由 | react-router-dom v7（HashRouter） |
| UI | Bootstrap 5 + Bootstrap Icons（全域載入 JS 供 dropdown/modal） |
| 匯出 | SheetJS（xlsx，僅前端寫檔） |
| 後端 | Supabase：Postgres 15、Auth、Storage、Edge Functions（Deno/TypeScript） |
| AI 辨識 | OpenAI `gpt-4o-mini` 或 Anthropic Claude（可於後台切換） |
| 通知 | LINE Messaging API（被動式，交易成功後觸發） |
| CI/CD | GitHub Actions → GitHub Pages |

## 四、資料範圍與權限（RLS）

- Helper：`is_admin()`、`my_location_id()`、`auth_profile()`
- 模式：**Admin（總管）不設限；Cadre（據點管理人員）／SocialWorker（物資小天使）以所屬據點限縮**（`role_name` 值不變，僅顯示名改名）
- 牽涉扣庫存的交易寫入一律關閉 client 端，改由 Edge Function 以 `service_role` 執行（函式自身先驗證角色/據點）
- **例外**：`supply_stock_in_log`（入庫捐贈人）、`supply_request`（舉手）開放 client 端寫入（RLS 限縮）；盤點調整 `stock_adjust`/`stock_adjust_delete` 自帶 `is_admin()` 檢查、授權 `authenticated` 直接呼叫
- 詳見 [資料庫與資料流.md](資料庫與資料流.md)

## 五、部署拓撲

```mermaid
flowchart LR
    Dev["本機 dev 分支"] -->|git push| DevRemote["origin/dev"]
    DevRemote -->|合併 (確認後)| Main["origin/main"]
    Main -->|push 觸發| GA["GitHub Actions<br/>deploy-pages.yml"]
    GA --> Pages["GitHub Pages 正式站"]
    Dev -.手動貼上.-> SQL["Supabase SQL Editor<br/>(migrations)"]
    Dev -.手動貼上.-> EF["Supabase Edge Functions<br/>(Via Editor)"]
```

- 前端隨 `main` 自動部署；**資料庫 migration 與 Edge Function 需手動於 Supabase Dashboard 部署**（貼上 `.sql` / `index.ts`）。
- 每次上正式站前建立 `backup-main-YYYYMMDD-N` 分支作為回復點。
